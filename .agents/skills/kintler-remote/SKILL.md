# Kintler: сразу к работе

Используй инструменты Kintler в их фактическом MCP namespace, не локальный терминал вместо удалённого. Не читай исходники/документацию для обычных операций. Если MCP отсутствует, настрой его сам по следующей процедуре, а не перекладывай установку на пользователя. Не настраивай SSH вместо Kintler.

## Автоматическое подключение AI

Запрос «подключись через Kintler / работай на другом ПК» разрешает настроить нужный локальный MCP и установить отсутствующий Controller, но НЕ разрешает менять сервер, профили владельца, чужие MCP-настройки или подтверждать удалённый доступ. Для ручной работы человека MCP вообще не нужен.

1. Определи фактический клиент/агентную среду, её активный harness и место запуска MCP, а не производителя модели. Если инструменты Kintler уже доступны, сразу переходи к выбору ПК. Иначе проверь существующие MCP её собственным менеджером/API/CLI. При подключённом сервере найди инструменты в её каталоге/Tool Search/Code Mode; не создавай дубликат. Не устанавливай OpenCode или другую агентную среду вместо текущей.
2. Сначала найди существующий Controller: путь пользователя, команда уже настроенного Kintler MCP, `PATH`, затем `%LOCALAPPDATA%\Programs\KintlerControl\KintlerController.exe`. Используй найденный EXE, в том числе переносной из другой папки; не заменяй его и не загружай вторую копию. Только если EXE не найден, вызови [scripts/install-controller.cmd](scripts/install-controller.cmd) через `cmd.exe /d /c`, сначала с `--check`, при коде `3` — без аргументов. Скрипт скачает официальный ZIP, проверит SHA-256 и запуск EXE, установит Controller и удалит свой staging. Коды `1`/`2` — отказ; не обходи проверку. GUI и MCP — режимы одного EXE: отдельный MCP-пакет не требуется.
3. Зарегистрируй сервер `kintler` нативным механизмом ТЕКУЩЕЙ среды. Единый контракт: **stdio**, команда — найденный абсолютный путь EXE, аргументы — `["--mcp"]`; процесс запускает сама среда. Прочитай только подходящий раздел [references/mcp-clients.md](references/mcp-clients.md): OpenCode, Codex, Claude Code/Desktop, Cursor, Antigravity, Gemini CLI, VS Code/Copilot или другая среда. Форматы JSON/TOML, переменные, scope и команды обновления не взаимозаменяемы. Изменяй только запись Kintler, сохраняя чужие серверы, комментарии и права; глобальную настройку делай только по запросу. Существующее другое подключение Kintler не перезаписывай вслепую. Персональные пути держи в локальных настройках или используй только поддерживаемые этой средой переменные; не публикуй их.
4. Обнови/переподключи сервер штатным способом этой среды, дождись успешного MCP initialize и каталога инструментов, затем проверь реальными `nodes()`/`capabilities()`. Созданный конфиг сам по себе не означает подключение. Если требуется подтверждение доверия пользователем, попроси только его, не отключай защиту. При ошибке остановись с причиной. Controller использует активный DPAPI-профиль: установка EXE не выдаёт ключ владельца. При отсутствии/ошибке профиля попроси выбрать существующий профиль в Controller, не генерируй замену владельца чужого сервера.

Совместимость клиента и ОС — разные вещи. Этот EXE запускается на Windows с профилем владельца; наличие MCP в Linux/macOS/облачной среде не делает Windows EXE исполняемым там. Для stdio нужен доступ к этому процессу. HTTP-only/облачный клиент потребует отдельно согласованного защищённого адаптера или поддерживаемого удалённого executor; не выдавай адрес relay Kintler за MCP HTTP endpoint и не открывай новые порты/публичный доступ автоматически. Для неизвестной среды выясни только её название/версию либо механизм регистрации MCP, затем используй её схему; не отказывай лишь потому, что это не OpenCode.

## Выбор и переключение ПК

1. Вызови `nodes()` и `capabilities()`. Устройство содержит `id`, `name`, `online`, `platform`, `admin`, `tools`; capabilities — права текущего оператора, не права каждого ПК.
2. Сопоставь запрошенное пользователем имя с единственным устройством и запомни его точный `id` как текущий `node`. Если цель не указана или имя неоднозначно, спроси; не выбирай первый ПК автоматически.
3. Проверь `online=true` и наличие нужного инструмента и в capabilities, и в `tools` устройства. При offline попроси запустить Agent на нужном ПК. Пользователь читает его крупный 6-значный код и вводит `/approve <номер> <код>` в терминале Controller для этого устройства. На ПК с Agent дополнительных кнопок не нужно. Код обязателен при КАЖДОМ подключении, даже знакомого устройства; после обрыва нужен новый код. MCP не предоставляет `approve`: AI не читает код сам и не подтверждает доступ вместо человека. После ручного подтверждения обнови `nodes()`; не ожидай бесконечно и не заявляй об успехе до `online=true`.
4. Кратко обозначь цель: «Работаю на NAME (ID)». Передавай этот точный `node` в КАЖДОМ удалённом вызове.

«Переключись на другой ПК» означает обновить `nodes()`, проверить новую цель и заменить текущий `node` только для последующих действий. Отдельного инструмента `select`/`switch` нет. Не переноси между ПК PID, `created`, рабочие каталоги, пути или разрешения. Для нескольких устройств храни отдельный контекст каждого; результат всегда подписывай его целью. Не перенаправляй уже начатую операцию на другой ПК.

## Все 12 инструментов

Это сигнатуры аргументов MCP, а не локальные Python-функции; `ctx` передавать не нужно.

| Вызов | Назначение и допустимые значения |
| --- | --- |
| `nodes()` | Доступные оператору устройства; не сканирование сети. |
| `capabilities()` | Разрешённые инструменты/узлы и срок сессии. |
| `sysinfo(node)` | ОС, ресурсы, диски, сеть и права. |
| `shell(node, command, interpreter="cmd", cwd=".", timeout=120)` | Windows: `cmd`; Linux: `bash`. `powershell` поддерживается Windows, но только если правила задачи допускают его. Таймаут 1–120 секунд. |
| `ps(node, sort="ram", limit=100)` | `sort`: `ram`, `cpu`, `pid`; `limit`: 1–500. Сохрани `created` вместе с PID. |
| `kill(node, pid, created, force=False)` | Только разрешённый процесс; PID и точный `created` возьми из свежего `ps` ЭТОГО ПК. Native Windows может завершать процесс немедленно даже с `force=False`. |
| `upload(node, local_path, remote_path, overwrite=False)` | Файл с ПК контроллера в workspace выбранного устройства; SHA-256 проверяется автоматически. |
| `download(node, remote_path, local_path, overwrite=False)` | Файл из workspace устройства на ПК контроллера; SHA-256 и атомарное сохранение. |
| `screenshot(node, local_path, monitor=1)` | PNG на ПК контроллера; `1` — первый монитор, `0` — весь рабочий стол. Нужен интерактивный desktop и разрешённый инструмент; копия остаётся в remote workspace. |
| `registry(node, key, operation="query", name="", value="", value_type="REG_SZ")` | Windows; чтение по ACL, `set` требует admin. Ключ начинается с `HKLM\`, `HKCU\`, `HKCR\`, `HKU\`, `HKCC\`. Типы: `REG_SZ`, `REG_EXPAND_SZ`, `REG_DWORD`, `REG_QWORD`, `REG_MULTI_SZ`, `REG_BINARY`. |
| `services(node, operation="list", name="")` | `list`/`status` по ACL; `start`/`stop` требуют Admin/root; `restart` — только Linux. `name` — системное имя службы, не отображаемая подпись. |
| `tasks(node, operation="list", name="", command="")` | Windows; `list` по ACL, `create` требует admin. Создание — задача `ONLOGON`, нужны `name` и `command`. Нет операций delete/run/update. |

## Пути, команды и передача между ПК

- `cwd` — существующий относительный каталог внутри workspace. Каждый `shell` — новый процесс: `cd`, переменные и состояние оболочки между вызовами не сохраняются. Для разрешённой работы вне workspace используй абсолютные пути внутри `command`, оставляя `cwd="."`; shell даёт OS-level доступ, а не sandbox.
- `remote_path` — относительный путь внутри workspace целевого ПК, без `..`, диска или абсолютного корня. `local_path` — путь на машине, где запущен MCP Controller, НЕ на выбранном ПК и не обязательно в файловой системе AI-среды. Укажи свободный путь; `overwrite=True` — только при разрешённой замене конкретного файла.
- A → B: `download(node=A, remote_path="file.bin", local_path=STAGING)` → `upload(node=B, local_path=STAGING, remote_path="file.bin")`. Оба вызова явно адресуй разным проверенным ID; прямого device-to-device инструмента нет. Удали только созданный тобой staging-файл на ПК контроллера после проверки результата. Не заявляй об удалении, если к этому ПК нет файлового доступа.

## Границы и проверка результата

Выполняй только запрошенную работу на явно выбранных, подключённых устройствах. Для kill, изменений реестра/служб/задач, удаления, перезаписи, установки или перезагрузки требуется разрешение пользователя на конкретное действие; выбор ПК сам по себе такого разрешения не даёт. Не повышай права и не обходи отключённый инструмент через shell. Секреты — только в локальном игнорируемом `.env`, не в командах, ответах или этом скилле.

Проверяй MCP `isError`, затем `ok`, `exit_code`, `stdout`/`stderr`; после изменения проверь состояние на том же `node`. При таймауте/обрыве результат изменения может быть неопределённым: сначала прочитай состояние, не повторяй запись вслепую. При отказе доступа остановись и сообщи причину. Убирай только свои временные файлы; рабочие данные, профили и резервные копии сохраняй.

# KintlerControl

**Ваш сервер. Ваши устройства. Ваше подтверждение.**

Self-hosted управление устройствами: лёгкий Windows-агент на Rust,
графический контроллер, MCP для AI-клиентов и relay в Docker.

## Что это

KintlerControl связывает ваши Windows-ПК через **ваш собственный сервер**.
Оба клиента устанавливают исходящие HTTPS/WSS-соединения: открывать входящие
порты на управляемом ПК и пробрасывать его SSH-порт не нужно.

**Каждое новое соединение агента требует подтверждения владельца.**
Повторный запуск, восстановление после разрыва сети и новая сессия после
истечения старой снова создают запрос — даже если устройство знакомое.
Сервер запоминает ключ устройства, **но не постоянное разрешение доступа**.

| Компонент | Назначение |
|---|---|
| `KintlerAgent.exe` | Нативный Rust/Win32 агент, без установки Python/WebView |
| `KintlerController.exe` | Самодостаточное приложение: устройства, запросы, инструменты, мастер, MCP и деплой |
| Docker relay | Аутентификация, маршрутизация, реестр и аудит |

### Инструменты

- `cmd`/PowerShell с потоковым выводом, таймаутом и отменой.
- Чанковый обмен файлами с SHA-256 и защитой от случайного перезаписывания.
- CPU/RAM, диски, сеть, инвентаризация GPU.
- Процессы и проверка времени создания PID перед завершением.
- PNG-снимки интерактивного рабочего стола Windows.
- Реестр, службы и планировщик Windows — при действительных правах Admin.
- 13 MCP-инструментов для разрешённых устройств, включая окно сообщения.

Используйте систему только на своих устройствах или с явным разрешением владельца.

## Быстрый запуск

### 1. Подготовьте сервер

Нужен Linux-сервер с Docker Engine и Compose plugin. Направьте DNS-имя,
например `relay.example.com`, на его IP. Для автоматического HTTPS нужны
свободные и доступные TCP **80/443**. Провайдер и страна размещения не ограничены.

### 2. Скачайте комплект

Скачайте **`KintlerControl-Bundle.zip`** из [Releases](https://github.com/vnkdevelop/kintlercontrol/releases/latest),
распакуйте на управляющем ПК и откройте `START_HERE.md`. Внутри: два EXE в `clients/windows/`, готовый образ и шаблоны в `server/`, скилл в `skills/kintler-remote/` и документация. Сам Controller по-прежнему переносится одним EXE.

Откройте **`clients/windows/KintlerController.exe`**, используйте **`/setup HTTPS_URL OUTPUT`**, укажите свой HTTPS-адрес и пустой каталог. Автоматический HTTPS — режим по умолчанию; для своего прокси добавьте `--mode existing-proxy`.

Мастер создаст:

```text
Ваш-комплект/
├── server-kit.zip       # этот архив отправить на сервер
├── server/              # Compose, публичная регистрация и инструкция
└── Agent/
    └── KintlerAgent.exe  # настроенный один EXE, без JSON
```

Приватный ключ владельца останется на этом ПК под Windows DPAPI.
В серверный комплект попадёт **только публичная регистрация**.

### 3. Запустите Docker

Загрузите `server-kit.zip` через SFTP/SCP и распакуйте в приватный каталог
приложения, не в web-root сайта. Выполните команду из `START_HERE.md`:

```bash
python3 start_server.py --check
python3 start_server.py
```

Caddy сам получает и продлевает HTTPS-сертификат. Прямой порт relay на хосте
доступен только через loopback, внешний трафик идёт через прокси.

Полный комплект включает готовый Docker image tar в `server/`. Мастер добавляет
его в server kit вместе с SHA-256 и самостоятельным `start_server.py`. Скрипт проверяет и загружает образ, скачивает недостающие образы вроде Caddy и запускает Compose. Вход в registry и пересборка образа пользователю не нужны. На сервере заранее нужны Python 3.10+, Docker и Compose. После запуска выполните `/reconnect` в Controller.

Уже есть Nginx/HTTPS-прокси? Выберите **Existing HTTPS proxy** и следуйте
[инструкции](docs/DEPLOYMENT.md). Не перезаписывайте работающую конфигурацию
сайтов и не запускайте второй listener на занятый порт.

### 4. Подключите ПК

Откройте **`KintlerController.exe`** у владельца. Перенесите сгенерированную
**KintlerAgent.exe** в любое место на целевом ПК и запустите агент. JSON, CMD и вспомогательные EXE не нужны.

В терминале Controller откройте `/approve`, выберите устройство и введите 6-значный код
из его Agent в появившемся поле. Это требуется и знакомым устройствам. Затем `/use имя` выбирает ПК,
а `/help` показывает команды с описаниями. Лишних панелей и ежедневной формы входа нет.

### 5. Подключите AI, если он нужен

В Controller выполните `/install-skill`: встроенный скилл установится локальным совместимым AI-клиентам. Затем попросите агента «работай через Kintler на ИМЯ». Он найдёт существующий Controller, настроит stdio MCP именно своей среды и проверит `nodes()`/`capabilities()`, без SSH, повторной установки и передачи ключа в конфиг. `/approve` остаётся действием человека.

Для отдельной установки AI доступны `KintlerControl-Skill.zip` и Controller EXE с SHA-256, без скачивания образа сервера. Подробнее: [AI_SETUP.md](docs/AI_SETUP.md), [структура проекта и личных данных](docs/PROJECT_LAYOUT.md).

> Знакомое устройство тоже требует нового кода и подтверждения на каждое соединение.
> Нет опции «всегда разрешать». Отказ и истечение ожидания не дают будущего доступа.

## Безопасность

- TLS **1.3**, проверка сертификата, без небезопасного Internet-режима.
- Индивидуальные **Ed25519**-ключи новых клиентов; приватные ключи не встроены
  в публичные EXE, репозиторий или server kit.
- Windows DPAPI защищает локальный ключ для исходного пользовательского контекста.
- Владелец регистрируется на сервере явно; неизвестный агент не может стать владельцем.
- Разрешение связано с конкретной живой socket/session и не работает для следующей.
- ACL на узлы/инструменты, локальная политика агента, права ОС и структурированный аудит.
- Ограничены соединения, очередь запросов, вывод и размер файлов.

**Границы:** relay доверенный и видит содержимое трафика. Это не E2E-шифрование,
не sandbox для shell, не TPM-аттестация и не независимая сертификация безопасности.
Полный shell получает права процесса агента. DPAPI не защищает от компрометации
исходного Windows-пользователя.

Подробнее: [SECURITY.md](SECURITY.md), [протокол](docs/API.md).

## Требования

| | Стартовый минимум | Рекомендуется |
|---|---|---|
| Сервер | Linux x86-64, 1 vCPU, 1 ГБ RAM | 2 vCPU, 2 ГБ RAM |
| Свободный диск | 5 ГБ | 10+ ГБ и мониторинг аудита |
| Runtime | Docker Engine + Compose plugin | Поддерживаемая актуальная версия |
| Сеть | DNS и доступный HTTPS | TCP 80/443 для автоматического TLS |
| Клиенты | Windows 10/11 x64 | Обновлённая ОС; desktop для скриншотов |

Минимум рассчитан на небольшое число устройств, а не является результатом
нагрузочного теста на максимальную ёмкость. Для активных команд и больших
передач нужны дополнительные ресурсы. GPU серверу не нужен.
Python/Rust на пользовательские ПК устанавливать **не требуется**.

## Ограничения

| Параметр | По умолчанию |
|---|---|
| Ожидание подтверждения | 10 минут |
| Ожидающие запросы | 64 всего, 4 на IP |
| Сессия | 1 час |
| Команда | До 120 секунд |
| Вывод команды | До 2 MiB |
| Файл | До 256 MiB |
| Активные команды | 64 всего, 8 на узел, 16 на сессию контроллера |

Поддерживается одна relay-реплика. Её перезапуск прерывает сессии и требует
новых подтверждений. Ключи-идентичности и аудит сохраняются в Docker volume.
**Не выполняйте `docker compose down -v` на рабочей установке.**

Shell неинтерактивный: нет PTY, RDP, управления мышью/клавиатурой или desktop-видео.
Административные инструменты требуют реальных прав Admin у агента.
Метрики GPU utilization для любых производителей не обещаются — доступна инвентаризация.

## AI / MCP

Команда **`/mcp`** контроллера показывает путь к этому же EXE и аргументы MCP.
Используйте формат MCP-настроек вашего клиента. Мост запускается локально по stdio,
а не как анонимный публичный endpoint.

Включайте подтверждения опасных инструментов. Удалённые файлы и stdout являются
недоверенными данными, а не инструкциями для AI.

## Разработка

```text
uv sync --locked --python 3.12 --extra dev --extra ai --extra screen --extra windows
uv run --no-sync pytest
uv run --no-sync ruff check .
uv run --no-sync mypy server agent client common scripts desktop deploy
```

На Windows с Rust и MSVC Build Tools:

```text
uv run --no-sync python -m scripts.build_windows
uv run --no-sync python -m scripts.windows_smoke
```

Проверки из `agent-rust/`: `cargo fmt --check`, `cargo clippy --locked -- -D warnings`,
`cargo test --locked`. Backend можно собрать `docker build -t kintlercontrol:dev .`;
для Compose-разработки используется дополнительный `docker-compose.dev.yml`.

## Один EXE, ярлык и деплой

Команда `/shortcut` или `KintlerController.exe --create-shortcut` создаёт нативный Windows-ярлык.
Активный защищённый профиль хранится в user data и не зависит от расположения EXE.
Мастер, MCP и CLI деплоя находятся в режимах этого же приложения.

Скрипт деплоя: `scripts/deploy_remote.py`. Шаблон `deploy/.env.example` копируется в игнорируемую папку как `.env`.
Сначала `KintlerController.exe --deploy --env PATH --dry-run`, затем обновление только своего Compose-проекта.
Приватные SSH-данные и настроенные персональные EXE не публикуются.
Подробнее: [docs/SINGLE_EXE.md](docs/SINGLE_EXE.md).
Терминальный интерфейс и команды: [docs/TERMINAL.md](docs/TERMINAL.md).

## Структура

`agent-rust/` — Windows-агент; `agent/` — совместимый Python/Linux-агент;
`server/` — relay/auth/approvals/router/audit; `client/` — CLI/SDK/MCP;
`desktop/` — контроллер и мастер; `deploy/` — шаблоны; `tests/` — регрессии.

`scripts/` — действующие команды сборки/проверки/релиза/деплоя;
`.agents/skills/` — скиллы. В `dist/windows/` находятся универсальные EXE и SHA-256,
в `dist/releases/` — архивы релизов. Настроенные личные клиенты —
`.private/clients/windows/`, личный серверный комплект — `.private/deployment/server/`,
текущие отчёты — `.private/reports/`. Подробнее: [структура и расположение клиентов](docs/PROJECT_LAYOUT.md).

`.env`, идентичности, deployments, базы, логи, EXE, build outputs и graph caches
исключены из Git. Публичные release-бинарники собираются из чистых исходников,
а не из персональной настроенной установки разработчика.
